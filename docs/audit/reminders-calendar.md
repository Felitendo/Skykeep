## Details: top items

### 1. Outbox ticks reach every screen, for every service
`useOutbox(service)` filters `waiting`/`refused` by service, but `tick` increments on every `CHANGED`. `CHANGED` carries no payload (`app.emit(CHANGED, ())`) and is sent before and after each drain of all four services. `Library.tsx:295-313` keeps visited screens mounted, so one Notes autosave does all of the following:
- Reminders runs `readItems` (`:541-544`), `remindersApi.marks` over every row (`:841-853`, findings 2 and 3), `readExtras` (finding 6), `reminders_ending` and `readDetail`, twice each.
- Calendar runs `read()` (`CalendarView.tsx:554-567`): events for about 3.5 months, `calendar_list`, `reminders_due_between`, `reminder_lists` and the feed list. Two of those build every contact (finding 9). The new `events` array then re-lays out Month/TimeGrid.

A reminder tick inside Reminders triggers the same cascade on top of `write()`'s own `readItems` (`:589`) and the `reminders-synced` listener (`:515`): about 4 list reads, 2 marks calls and 2 N+1 tag sweeps per tick, all waiting on one mutex. This is where the "tick feels late" and "everything stalls while typing a note" latency comes from.
**Fix:** `emit(CHANGED, ChangedPayload { services })` with the services that had pending or sent items. In `useOutbox`, `listen<{services:string[]}>(CHANGED, e => { read(); if (!e.payload?.services || e.payload.services.includes(service)) setTick(n=>n+1); })`. Drop the pre-drain emit when nothing is queued for that service.

### 2 and 3. `reminder_marks`: lock-heavy, unindexed, network-gated
- Lock: `let library = data.0.lock().await;` (`reminders_cmds.rs:103`) is held across the whole `for guid in guids.iter().take(2_000)` loop. Each guid runs 5–6 queries, `serde_json` parses the raw record (several KB), and `contact_name_for` loads the **entire** `contact_methods` table for each reminder that has a messaging person (`reminders.rs:3599-3610`).
- Index: `reminder_parts` (`reminders.rs:3518-3524`) has `JOIN reminder_alarms a ... WHERE a.reminder_guid = ?1`. The only index on that table is `reminder_alarms_by_trigger(trigger_id)` (`schema.rs:350`), so 1,000 rows mean 1,000 scans of every alarm, completed reminders' alarms included.
- Network: after the lock, up to 40 `urgent_for` calls are awaited before the IPC returns. `URGENT_SEEN` is filled only on success (`reminders_more.rs:288-291,313-317`), so a lapsed `downloadURL` or offline state retries all 40 on every call.

Visible effect: open a list and the rows draw. Seconds later the chips row (Weekdays, place, link) appears and every affected row grows by a line, which is a visible jump. Meanwhile a tick's `set_done` waits on the mutex.
**Fix:** add the index. Build marks with a few set-based queries keyed by `IN (…)`, and load `contact_methods` once. Return without Urgent, then spawn the Urgent fetch and `emit("quince://reminder-urgent", Vec<(guid,bool)>)`. The UI merges the result into `marks`. Store `None` results with a timestamp so failures are not retried on every call.

### 4. Full-zone re-sync after detail and list writes
`resync_reminders` passes `whole = true`, so `since = None` (`main.rs:173-182`). That walks the entire zone, including years of completed reminders, and `fetch_memberships` downloads one file per list in sequence (`reminders.rs:741-770`). The apply step then rewrites every row and alarm (`put_alarms(..., whole)` deletes and re-inserts all alarms) inside one transaction on the library lock. Callers include `finish()` in `reminders_cmds.rs:189-200` (tags, URL, early alert, sections), `reminder_reorder`, `reminder_set_repeat` and the list commands in `main.rs`. A drag-reorder, for example, keeps the reminder's write queue (`RemindersView.tsx:579-582`) busy for the whole walk. The comment's reason ("a list change moves records other than the one written") does not need a whole pass: a token-based walk returns every record changed since the token, the side-moved ones included.
**Fix:** `refresh_reminders(http, root, params, data, false)`. Keep `whole` for an explicit "Refresh" or a refused cursor, which `fetch_cloudkit` already detects.

### 5. 1,000-row list without memoisation
All row JSX is produced inside `sections.map(... section.rows.map(...))`, so any state change in `RemindersView` re-runs it all. Examples:
- **Typing a new reminder**: `setDraft` on each key reconciles every row's `<input>`, chips and handlers.
- **Dragging**: `setDragging` on drag start and `setDropBefore` each time the hovered row changes. Each one is a full-list render while the pointer moves.
- **Ticking**: `setItems(patch)`, then `setSettling`, then `setLeaving` 600 ms later, then `setDeparted` and the confirming `readItems`. That is 4–6 full renders per tick, plus the ones from finding 1.

WebKitGTK is the slowest engine here, and 1,000 rows of about 25 nodes each is roughly 25k nodes diffed per keystroke.
**Fix:** move the row body into `const ReminderRow = memo(...)` with props `{reminder, depth, isOpen, mark, tags, colour, dated, showList, dropBefore:boolean, ...}`. Pass actions through a single stable `actions` ref object. Build a `Map` from list guid to list once per `lists`. For the drop marker, set `el.classList.toggle("is-drop-before")` in `onDragOver` instead of React state. Add `content-visibility:auto` to `.rx-row` so off-screen rows are not laid out or painted. It is opacity-free and not a compositor animation, so it is safe for the Hyprland flicker rule.

### 6. Tag and smart-list N+1
With T tags and C custom lists, every `readExtras` call makes T + C + 2 IPC calls, and they serialise on `data.0.lock()`. Each `reminders_tagged` builds and serialises up to 1,000 full reminders. One `SELECT reminder_guid, name FROM reminder_hashtags` (already written as `all_tags_by_reminder`, `reminders.rs:2950-2960`) returns the same map in a single query.

### 7. Notes blur writes unconditionally
`onBlur={(e) => void setNotes(reminder, e.target.value)}` (`RemindersView.tsx:2098`) calls `write(r, () => api.reminderEdit(..., { notes }))` with no comparison. The backend queues it (`outbox_append`) and lays it on the library immediately, so the phone's newer notes are overwritten locally and then at Apple when the outbox sends. Pressing Tab through the detail panel is enough to trigger it.

### 8. Calendar delete and duplicate wait on Apple
`remove` (`CalendarView.tsx:761-788`) reaches `await api.eventAlerts(guid)` before `write(...)` applies the predicted removal. That command goes to Apple each time (`main.rs:1680-1697`). The same applies to ⌘D (`:811-822`). This breaks the "instant everywhere" rule: offline, Delete looks broken until reqwest times out.

### 10. Year view loses open reminders
`reminders_due_between` has `WHERE ... r.due_at >= ?1 AND r.due_at < ?2 ORDER BY r.due_at LIMIT 1000` with no completed filter. The year range covers 12 months of completed one-offs, and the client then discards them (`filter((r) => !r.completedAt)`). Once a year holds more than 1,000 dated reminders, the open ones in later months are cut off. Adding `AND r.completed_at IS NULL` uses the same `reminders_by_due` index.

## Checked and fine
- Calendar search is debounced (120 ms). TimeGrid drag renders only when the position moves to a new quarter-hour. MonthView, TimeGrid and YearView are memoised, and `byDay` is computed once.
- Date formatters are cached (`src/lib/when.ts`), the row fade uses opacity drawn by the page, and the popover has no open animation.
- Reminder tick, edit, create and delete and event save/delete go through the outbox, so they are local first.
- The repeat-tick double-click guard (`held` ref) is correct, and alarms ring once (`alarm_fired`) with a sleep and resume wake-up.
- No `unwrap` or `expect` on network input in non-test Reminders and Calendar code, apart from finding 13.

## Summary
Main causes: outbox ticks that ignore the service (1), plus a lock-heavy, unindexed `reminder_marks` that waits on the network (2, 3), stall Reminders and Calendar even while you work in Notes.
Writes run a full-zone CloudKit re-sync (4), and an unmemoised list of up to 1,000 rows re-renders on every keystroke, drag move and tick (5).
Data safety: blurring Notes can overwrite a newer phone edit (7). Calendar delete and duplicate wait on the network (8), and Year view can drop open reminders (10).
